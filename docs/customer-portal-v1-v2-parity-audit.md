# Customer portal V1 → V2 parity audit

Audit date: November 5, 2026 (Asia/Kolkata). Scope: hosted customer portal **and** merchant configuration affecting it. This is an audit, not an implementation change.

Repository snapshots: V1 `870d8ca7ecbbbe670789171de4c158afc1337646`; V2 `8b3c77762619d4f47dd7df90604dbbd10090ba9a`. Both tracked working trees were clean when investigation began. Runtime behavior below is from local builds against the configured development API, not production deployment certification.

## 1. Executive summary

**Parity is incomplete. Do not approve the migration based on the presence of four pages.** The strongest reproduced regression is checkout identity: requesting USD 2 in V2 reopens an existing USD 1 Stripe sandbox session while telling the customer to finish paying USD 2. V1 explicitly warns that a checkout is already in progress. The second reproduced regression is historical wallet data: V2’s “All transactions” can return an empty state for a wallet whose older transactions V1 displays.

The audit includes source tracing, 123 passing targeted unit tests, two passing mocked Chromium journeys, and live browser comparison in the same tenant and sandbox. Live coverage includes two environments and matching customer identities, subscription reads, invoices with tax, usage aggregation and property grouping, existing cards after a user added one, and Stripe sandbox handoff/recovery. Successful charging, webhook completion, permission-negative scenarios, settings writes, and regional deployments remain unverified. No backend repository was available; no backend change is asserted as necessary without contract evidence.

### Requested capabilities not discovered as V1 hosted-customer workflows

These are **not migration gaps** merely because they appeared in the requested checklist:

- Customer password login/reset/change, email verification, logout and account security. V1 hosted access is a bearer session link. Admin Supabase login is a different surface.
- Customer subscription cancel/renew/pause/resume, upgrade/downgrade, plan switch, proration preview, pending plan-change management or subscription history. The hosted SubscriptionsWidget is read-only. Admin subscription forms do not establish customer capability.
- Public plan catalog/comparison, monthly/annual plan selection, plan/add-on/one-time-product checkout. V1’s Pricing Widget and admin Plans/Add-ons are separate surfaces; the hosted portal exposes wallet purchase and invoice payment.
- Customer profile, address, tax-ID/company editing. `updateCustomer` exists in the V1 service, but no hosted form invokes it. V2’s unused PUT `/info` wrapper is likewise not a completed customer workflow.
- Customer notification preferences or a general activity feed. Billing status, credit ledger and checkout feedback exist; the unused EventsTable component does not establish an accessible portal events route.
- Merchant portal master enable/disable, custom hosted domain/URL editor, portal name/content editor, or separate customer cancel/upgrade/profile-edit permission flags. Section visibility and provider capabilities are the controls actually found. All-sections-off is not a documented security kill switch.
- Logo upload/editor: `logo_url` exists in V1’s type, but current PortalHeader does not render it and no current merchant editor was found. Theme typing is not proof of persistence.

### V1 behaviors that should not be copied as requirements

The standalone Payments section is explicitly retired in `deepMergePortalConfig`; cards moved to Overview. The legacy payments visibility switch can be off while Overview still shows cards (reproduced in Harshit’s home). V1’s “Reset to defaults” on this page restores the loaded **draft**, rather than deleting the stored setting. V1’s balance/top-up widgets independently pick the first active wallet even when its history dropdown selects another wallet. V2’s shared wallet selection improves that inconsistency. V1 list pagination is itself capped for invoices/subscriptions; parity should preserve access and then remove both caps, not reproduce them.

### API comparison (paths include `/v1`)

Both portals use `/v1/customer/portal` for customer data and actions. V1’s Axios base supplies `/v1`; V2 explicitly prefixes it. V2 deliberately uses `publicRequest` for these routes because they are not represented by the generated authenticated SDK. Plain fetch here is **not** a missing integration.

## 5. Missing and incomplete functionality

Each finding below specifies the missing work and its dependency. The IDs in parentheses are matrix units, not additional counted features. All **Missing**, **Partial**, and **Broken** rows have a task or verification action here or in section 9.

### P0-01 — Existing checkout is presented as a new purchase (E04)

- **Module:** wallet checkout, hosted `/p/credits` and Overview Add credits.
- **V1:** `TopUpForm` reads `checkout_session.entity_creation_result` before any URL/status. `PendingCheckoutDialog` offers continue or explicit restart using `entity_creation_options`.
- **V2:** `usePortalAction` reduces every successful HTTP response to `toPortalActionUrl`; `AddCreditsDialog` labels it with the requested amount, never the returned existing session’s amount. No entity-creation result or session ID survives mapping.
- **Reproduction:** in Harshit’s home / PUP Acme / Postpaid Wallet USD, V1 initiated a 1-credit USD 1 Stripe **sandbox** session. V2 submitted 1 credit and then 2 credits. Both V2 responses linked the identical original USD 1 session; V2 said “Finish paying $2.00 in the new tab.” The hosted Stripe item still said “Purchase 1 Credits ($1).” Repeating 2 credits in V1 instead produced “A payment is already in progress.” No payment was completed.
- **Expected:** show that an existing purchase blocks this request; label its actual amount/provider; resume or ask before superseding. Never imply credits requested by a new form are the credits purchased by an older session.
- **Implementation:** preserve typed session/result/status/amount/action information in domain/query, add explicit blocked state and supersede mutation option to UI. API dependency is already demonstrated by V1 behavior; no new backend endpoint is established as necessary.
- **Files:** V1-T, V1-R; V2-D, V2-Q, V2-F. Review saved-card branch too: it discards a returned redirect URL through `settle`, so a non-immediate action may be lost.

### P1-01 — “All transactions” omits historical wallet activity (H02–H04)

- **V1:** ledger can page through transactions across all dates. **V2:** `PortalSurface` passes the **first active subscription** start into `usePortalWalletTransactionPages`; it is also used for added/used totals. No all-time or date selection is offered for the ledger.
- **Live evidence:** PUP Acme’s prepaid wallet has November 3 entries: manual debit 8,898 and purchased credits 876, 786 and 12. V2 selected a November 5 subscription boundary and showed “Nothing here yet” under “Every credit added to and used from this wallet.” Its separate Top-ups table still showed the November 3 credits. This contradiction is visible in the screenshots.
- **Expected:** default history includes all wallet transactions, or explicitly offers an all-time view and labels any selected filter. Use a wallet ledger period rather than an arbitrary subscription when subscriptions differ.
- **Implementation/dependency:** frontend-only existing GET ledger; retain offset pagination, reset per wallet, remove implicit `since` for full history. Provide real pagination for credit-grant/top-up list beyond 100; `onShowMoreTopUps` is currently a no-op. Preserve pending status when displaying credit remaining rather than implying unpaid credits are spendable.

### P1-02 — Checkout result lifecycle and retry identity incomplete (E02–E07)

- V1 remembers checkout IDs, polls boundedly, distinguishes completed/failed/expired, reports failure reason, and coordinates return tabs. V2 keeps only an action URL; immediate no-URL results close the form without inspecting failure/pending status. Its message claims the page updates by itself, while no checkout-status polling exists.
- V1 top-up fingerprint rotates idempotency keys on payload edits; V2 retains a hook-wide key after failure even if wallet/amount/provider/invoice changes. A changed request can receive old results or a key-conflict response. Conversely the key is reset on a healthy HTTP response even when that response names a blocked or nonterminal session.
- Expected: typed outcomes, immutable attempt fingerprint and recoverable session state across reload/return; no success inferred from missing URL. Cancel/failure return should preserve the right customer without leaking token in return URLs. V1’s Stripe Back link was tokenless and returned to V1; V2 reused that old session, so this reproduction also returned to **V1**, not the initiating V2 portal.
- Dependency: frontend reuse of existing checkout APIs; webhook timing and real provider success/failure need controlled integration verification. Chargebee/Razorpay checkout not completed or certified.

### P1-03 — Auto top-up cannot clear cooldown and loses exact units (H05–H07)

V1 sends `{cooldown:{value:0,unit}}` to clear a stored duration. V2 returns `null` from the unchecked cooloff switch and omits the field in the PUT. Its own update does not ask the backend to clear anything. `cooldownOf` additionally rounds seconds up to minutes, and the editor omits seconds. Preserve exact stored values and send the explicit reset sentinel. Validate positive threshold/amount before submission; V2’s submit gate checks card presence, while parsed invalid amounts can become omitted fields. Confirm threshold/amount units with a non-unit conversion wallet: V1 labels them currency, V2 labels them credits; API field names alone do not resolve the contract. No auto-top-up writes were performed in this audit.

### P1-04 — Real-time balance and total-debt coverage reduced (B02, H01)

V1 credit balance fetches GET `/wallets/{id}` separately and prefers the real-time response; V2 depends solely on list fields and falls back to stored `balance`/`credit_balance`. Restore the distinct real-time read or obtain and test a backend guarantee that the list contains equally current values. For amount due, V1’s configurable account summary reads up to 20 pages of 100; V2 sums only one invoice page. Add pagination/aggregate coverage with a completeness indicator and currency-separated totals. Do not sum currencies. V2’s `totalDue` already excludes other currencies and reports the count; retain that improvement while extending coverage.

### P1-05 — Card eligibility and provider failures are discarded (G05–G06, B03)

V1 requires card `status === ACTIVE` and `can_auto_charge`, and displays each provider’s error. V2’s mapper retains neither field nor provider error. Selection requires a default unexpired card and provider `autoCharge`, permitting an inactive/non-chargeable default and refusing an otherwise chargeable non-default. Preserve eligibility/errors, allow the documented eligible fallback and do not label provider outage as zero cards. With no configured provider (Revrec Demo Co), V1 says payment methods are unavailable; V2 invites saving a card without offering Add card. The user-added default Chargebee Visa was visible after refresh in both, but that does not exercise inactive/error variants or charging.

### P1-06 — Shared usage filtering and custom metrics not migrated (I03–I07)

V1 sends multi-feature `feature_ids` and `property_filters` to its analytics queries. In Harshit’s home, applying `team=team-15` changes the same 30-day spend from 2,656.35 to 289.11. V2 lacks property-values requests and a property-filter payload, and only its trend has a local single-feature picker. Its property grouping updates breakdown, not trend/summary. Add shared feature/filter/group state and apply it consistently. Restore `custom_analytics` cards and opt-in cost/margin reads or record a product decision; retaining no-op admin switches is not acceptable. Do not expose cost/margin by default: V1 explicitly requires opt-in.

### P1-07 — Stored settings and hosted consumption diverge (S01–S09)

V2 edits an ordered tree but renders a fixed four-view/fixed-part composition. Unknown/custom section IDs and widget types are ignored; tab ordering is discarded. The admin card controls for custom/cost are saved but have no effect. Secondary/tertiary theme values are editable but the hosted mapper uses only primary. Configured feature IDs and widget labels are not retained by the typed settings codec. This is distinct from a backend storage guarantee: optional V1 fields may themselves not have been supported server-side. Preserve unknown data until contract support is established; disable unsupported editors or explain product-approved replacements. If every stored section is off, V2 forces Overview back on; the setting must not be represented as a portal disable switch. Deep invoice query/action and read requests are not gated merely by hiding navigation.

### P1-08 — Labeled onboarding workflows absent (M05)

V1 `CustomerOnboarding` supports `custom_workflows` keyed by label, and `CustomWorkflowCard`/`OnboardingActionSetEditor` edit wallet/subscription provisioning with initial credits/expiry. V2’s `toCustomerOnboarding`/request models return only `workflow_type` and `actions`. Restore labeled workflow read/edit/write and unknown-field preservation, or document the intended replacement. Whether a save deletes stored custom workflows depends on generic settings merge behavior; it is a **risk to verify**, not a proven deletion. These defaults affect what customers find in the portal but are not portal authentication/onboarding screens.

### P2-01 — Invoice export, information and boundary gaps (F01–F09)

Restore line-item CSV alongside PDF; preserve zero-value/included lines that V1 shows. Normalize invoice period end consistently: V1 invoice drawer shows an exclusive November 1 endpoint as October 31, while V2 prints November 1. Verify PDF `url=true` on the live API before claiming that removing it works. Page invoice history beyond 50 and test refunded/processing/void/failed combinations. The V2 detail’s “Payment” block uses the account’s **current default card**, not a transaction-specific payment record; do not imply this card paid a historical invoice. This added information should be sourced correctly or labeled as card on file.

### P2-02 — Link migration, localization and account identity (A06, U01, B01)

Add V1 link/settings-query translations or publish an explicit transition policy. Restore English/Arabic portal strings and RTL verification; Intl formatting is not equivalent. V2 hides customer name/email below `sm`, leaving initials only; keep usable account identity for small viewports. V1 forced light mode; V2 follows ThemeProvider/system. This is a documented code choice, but no product decision was found approving loss of V1 tenant theme fields. Treat branding compatibility as an open migration decision rather than inventing a new theme in the page.

### P3-01 — Verification and presentation follow-ups (U02, I02, M04)

Check complete keyboard/focus/scroll flow, narrow-width table actions, configured custom-currency symbols, per-provider default preferences and exact analytics bucket labels. In live 30-day V2 usage the selected label began October 7 while the chart’s first tick read October 6; this observation needs API bucket/timezone inspection before diagnosing an offset bug. Existing mocked E2E emitted React warnings about script tags and duplicate `closed` keys; tests still passed and these warnings alone do not prove a broken journey.

### Persistence and enforcement contract

Admin settings use authenticated `/v1/settings/{key}` GET/PUT with `{value: ...}`, and DELETE for server-default reset in V2. V2 `useSettingUpdate` validates selected environment, fetches auth token, writes the API response into the environment-specific query key and invalidates with `refetchType:'none'`; its comments explain replica-lag avoidance. That is **source evidence**, not a write/reload result from this audit. V1 portal settings PUT also sends the whole tree; contrary to a stale explanatory comment in V2, the current V1 `applyPortalVisibility` preserves sibling sections/tabs instead of rebuilding a five-boolean object. This audit uses the actual current implementation.

Hosted GET `/config` returns `{value: ...}`. V2 maps it into four known views and booleans, not a generic ordered widget tree. V2 still issues customer, config, integrations, subscriptions, invoices, wallets, payment methods, quota and spend queries before applying visibility. A disabled part is presentation, not proof that its API is inaccessible. Server-side tenant/environment/customer scoping, allowed/hidden analytics keys and mutation restrictions require independent backend/negative testing. Never promote a hidden control to an authorization guarantee.
