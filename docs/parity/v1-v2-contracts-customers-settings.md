# V1 → V2 parity: contracts, customers, settings

A screen-by-screen audit of what the V1 dashboard (`flexprice-front`) does in
**subscriptions, customers and settings**, and whether the V2 console does it
too. It is the working map for the parity push before V2 replaces V1 for
customers. Everything here was read from code on both sides, not inferred from
file names.

**Status: 2026-10-22**, measured against `develop` at `85bb4944` and
`flexprice-front` at `d19dbdac`. Parallel work is already closing some of these
rows (customer entitlement usage, customer analytics table, contract
commitment, inheritance). Re-check a row before acting on it.

- **V1 paths** are relative to `flexprice-front/src/`.
- **V2 paths** are relative to this repository's root.
- Line numbers are approximate where marked `~`.

| Status      | Meaning                                                                                                              |
| ----------- | -------------------------------------------------------------------------------------------------------------------- |
| **Present** | V2 does what V1 did.                                                                                                 |
| **Partial** | V2 does some of it; the note says exactly what is missing.                                                           |
| **Missing** | V2 has no equivalent.                                                                                                |

## Contracts (V1 subscriptions)

Renaming "subscription" to "contract" is intentional and is not counted as a gap. V1 subscription pages: `pages/customer/subscriptions/`, `pages/customer/customers/*Subscription*`, `components/organisms/Subscription/`. V2: `apps/console/src/pages/subscriptions/`, `packages/ui/src/pages/contracts/`.

### How V2 is laid out

- Routes: `/contracts` (list), `/contracts/new` (a stepper with the step in the URL), `/contracts/$subscriptionId` (detail), and `/customers/$customerId/contracts/new` (create for one customer; the old `/subscriptions/new` alias still works). See `apps/console/src/app/router.tsx:716-760`.
- RBAC: `apps/console/src/app/access/routeAccess.ts:80-84` gives the list and detail pages read access to `subscription`, and the create pages write access. `RouteAccessGate` wraps every page in `AccessScope`, so list create buttons and row actions turn off without write access. Detail sections use their own scope: entitlement and credit grant sections call `PartSection entity=…` (`packages/ui/src/pages/contracts/SubscriptionDetailView.tsx:1861-1910`).
- **V2 has no separate edit page.** The detail page also does the editing, which **is an intentional change**: charges, entitlements, credit grants, add-ons, coupons and taxes are all edited there. The prior-decision docs are out of date:
  - `docs/v1-v2-gap.md:24` lists subscription update, add-add-on and line-item operations as "Not yet", and `:43` lists the subscription edit route as missing. All of these are now bound in `packages/query/src/subscriptions.ts`: `useCreate/Update/DeleteSubscriptionLineItem`, `useAddSubscriptionAddon`, `usePreviewLineChange` and `useExecuteLineChange`.
  - `docs/v2-capability-gaps.md` says **nothing** about subscriptions or contracts. **None of the gaps below is recorded anywhere as a deliberate decision.**

### Results for the three suspected gaps

1. **Usage bar on contract entitlements. Not a V1 contract feature, so it is not a regression.**
   - V1's subscription detail page (`pages/customer/customers/CustomerSubscriptionDetailsPage.tsx`) has **no entitlements section**.
   - V1's subscription edit page shows entitlements through `components/molecules/SubscriptionEntitlementsSection/SubscriptionEntitlementsSection.tsx`, with no usage bar. Its columns are feature, type chip, value with an override tooltip, and source (plan, add-on, subscription or override). Row actions are edit and delete, plus "Add".
   - V1's only entitlement usage bars are on the **customer** Overview tab: `pages/customer/tabs/CustomerOverviewTab.tsx:328` uses `CustomerUsageTable` with `<Progress>` at `components/molecules/CustomerUsageTable/CustomerUsageTable.tsx:281,300`.
   - V2 has the same thing on the customer page: `UsageSection` with `QuotaCard` in `apps/console/src/pages/customers/CustomerDetailPage.tsx:292-360` and `packages/ui/src/pages/shared/QuotaCard.tsx`.
   - **The real V2 gap is the contract entitlement table itself** (`SubscriptionDetailView.tsx:833-880`):
     - It has only three columns: Feature, Access and Limit.
     - It has no feature type, no source column and no "override of plan" marker.
     - It cannot show static or config values or grant-style allowances. `toSubscriptionEntitlement` in `packages/query/src/subscriptions.ts:411` keeps only `isEnabled`, `usageLimit`, `isSoftLimit` and `usageResetPeriod`.
     - It has **no edit and no delete**, only Add.
2. **Contract-level commitment. Present at creation; partial on the detail page; V1 never allowed editing it after creation.**
   - At creation:
     - V1 has commitment amount, commitment period (daily to annual or "same as billing"), overage factor and an enable-true-up switch (`components/organisms/Subscription/SubscriptionForm.tsx:1015-1060`).
     - V2 has the same four fields in step 3 under "Contract commitment" (`packages/ui/src/pages/contracts/SubscriptionForm.tsx:2506-2580`, mapped in `packages/query/src/subscriptions.ts:686+`).
   - On the detail page:
     - V1 shows the commitment amount with its period, a separate "Commitment period" row, and the overage factor when it is above 1 (`CustomerSubscriptionDetailsPage.tsx:340-345,405-430`). Usage lines carry a tooltip with amount, overage, true-up and duration (`components/molecules/SubscriptionLineItemTable/SubscriptionLineItemTable.tsx:362-400`).
     - V2 shows **only** the amount, plus "· X used" from usage (`SubscriptionDetailView.tsx:1600-1604`). `SubscriptionDetail` has no `commitmentDuration`, `overageFactor` or `enableTrueUp` (`packages/domain/src/subscription.ts:600-620`), so the period, overage factor and true-up are **not shown**. The V2 "Commitments" section (`SubscriptionDetailView.tsx:789-830`) covers **charge-level** commitments only.
   - Editing after creation: V1 has no editor for the contract commitment on its edit page; it only displays it in `SubscriptionEditDetailsHeader`. So V2 is not missing an editor V1 had.
3. **"Inherited customers" at creation. Present, with a scale limit. The inheritance work after creation is missing.**
   - V1 at creation: an `InheritedCustomersTable` with async customer search (`SubscriptionForm.tsx:1206`), sent as `inheritance.external_customer_ids_to_inherit_subscription` (`CreateCustomerSubscriptionPage.tsx:~800`).
   - V2 at creation: an "Inherited customers" multi-pick in step 4 under "Customer hierarchy" (`packages/ui/src/pages/contracts/SubscriptionForm.tsx:2998-3050`), sent at `packages/query/src/subscriptions.ts:790-800`.
     - **Limit:** the choices are only the first 100 customers that have an external ID. The page loads them with `PICKER_PAGE = {pageSize: 100}` (`apps/console/src/pages/subscriptions/SubscriptionFormPage.tsx:51,63`), and there is no server search.
   - **After creation, all of this is missing in V2:**
     - The list of child contracts on the parent (V1 detail `:178-250,560-575`).
     - Adding or detaching inheriting customers (V1 edit `components/molecules/Subscription/SubscriptionEditInheritingCustomersSection.tsx`).
     - Setting a parent subscription (`components/molecules/UpdateSubscriptionDrawer`).
     - Showing the parent customer or the invoicing customer, and the subscription-type chip.
     - The read-only guard on inherited contracts (`isInheritedSubscription`).
     - `parentSubscriptionId`, `invoicingCustomerId` and `subscriptionType` appear nowhere in V2's `packages/{query,domain,ui}`.

#### 4a. Suspected gap 1, confirmed: entitlements with usage bars

**V1 behaviour.** The table sits on the Overview tab and appears only when there are features. Source: `CustomerOverviewTab.tsx:325-330`, data from `CustomerApi.getUsageSummary`. One row per feature, or one row per budget for "parallel" features (buckets). Columns, from `CustomerUsageTable.tsx:130-295`:

1. **Feature**: feature-type chip and name, linking to the feature.
2. **Source**: the plan, add-on or subscription that grants it. It links to that entity and shows "+N" with a tooltip when there are several.
3. **Value**:
   - Metered: limit per period, e.g. "50 / billing period", or Unlimited.
   - Boolean: true/false.
   - Static: the static value.
   - Config: the config JSON.
4. **Mode**: Additive or Parallel.
5. **Measure**: Quantity or Amount.
6. **Usage**: a progress bar labelled "used / limit". It turns red at 100% or more and shows an "unlimited" variant.

Clicking a row opens `GrantWindowLedger` (Start, End, Status, Usage, with an overage tooltip) for grant-backed rows.

**V2 behaviour.** Entitlements are **not on Overview**. A "Usage" section of `QuotaCard`s sits **under the Analytics tab**. Source: `apps/console/src/pages/customers/CustomerDetailPage.tsx:254-259, 314-375`, `packages/ui/src/pages/shared/QuotaCard.tsx`. Each card shows the feature name, used, included (null = unlimited), percent, a progress bar (amber above 85%, red when over), remaining, "Over by", and the reset date.

What V2 loses:

- **Source** (granting plan, add-on or subscription) and its links.
- **Mode** (parallel/additive) and per-budget rows; the domain `TenantFeatureUsage` has no buckets (`packages/domain/src/tenant.ts:138-154`).
- **Measure** (quantity or amount).
- The grant-window ledger drill-down.
- A link to the feature.
- Units: `unit_plural` is dropped (comment at CustomerDetailPage.tsx:310-312).
- Correct treatment of **boolean, static and config features**. `featureType` is ignored in `UsageSection`, so a boolean or static entitlement (limit null) renders as an "unlimited" usage card instead of "Enabled" or its static value.
- The period-relative allowance label ("50 / day").

#### 9a. Suspected gap 2: V1 analytics table vs V2 cards. Partly confirmed, with a correction.

**V1 is a table.** It is `UsageDataTable`, titled "Usage breakdown", in `CustomerAnalyticsTab.tsx:640-783`. Its columns:

1. **Feature**: the name, linking to the feature in a new tab.
2. **Total usage**: uses `total_usage_display` when present, with the reporting unit chosen singular or plural.
3. **Revenue**: `total_cost` with a PriceTooltip, which shows the price and flags subscription-override prices.
4. **COGS**: from the merged cost analytics.
5. **Margin**: signed.

How the table behaves:

- Usage, Revenue, COGS and Margin are sortable; the default sort is Revenue, descending.
- Rows are **grouped by feature group**. Each group has an expandable header row carrying aggregate Revenue, COGS and Margin, plus an expand-all/collapse-all control. Ungrouped rows are listed after the groups.
- One feature can appear more than once, keyed by price or meter (`sub_line_item_id`).
- Features with zero usage are filtered out.

Beside it:

- A second "Cost breakdown" table (Cost attribute, Total quantity, Total cost) lists unmatched cost items.
- Tiles above the table show Revenue, Cost, Margin, Margin % and CPM.

**V2 is tiles plus a table, then cards.** The suspected "usage shown as cards" is only half true.

The wired Analytics tab (`CustomerDetailPage.tsx:240-261`) has three parts:

- (a) Four `OverviewTiles` (Usage revenue, Events, Features used, Period "Last 30 days"; `CustomerUsageSummary.tsx:52-66`).
- (b) A **table**, "Usage by feature" (`CustomerUsageSummary.tsx:68-117`), with three columns:
  - **Feature**: name, with the lookup key underneath.
  - **Events**: a count.
  - **Usage**: the formatted quantity and unit.
  - Sortable on Feature and Events, with client-side search.
- (c) The entitlement **QuotaCards** (§4a), which are cards.

Compared with V1's table, the V2 table is missing:

- Revenue, COGS and Margin per feature.
- Feature-group grouping and its aggregates.
- Price tooltips and override flags.
- Multiple rows per price.
- Display/reporting units.
- The feature link.
- Any date, feature or children filter.

The tiles lose Cost, Margin, Margin % and CPM. The cost-breakdown table is gone.

`CustomerAnalyticsView.tsx` is a closer match: it has a feature filter, From/To dates, Include children, Revenue/Cost/Margin/Margin % tiles, and a table with Feature, Usage, Revenue, Cost and Share of revenue. But it is **demo-only**: exported, never mounted, with hardcoded USD, a fake sine-wave series (`seriesFor`), and `DEMO_FEATURE_ANALYTICS`. It should not be mistaken for shipped parity.
